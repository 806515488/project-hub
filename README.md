# project-hub

**跨 AI 工具的项目维护架构安装器** —— 为任何项目一次性建立「PROJECT.md 单一事实源 + 各 AI 工具入口文件」体系。安装完成后体系自转，skill 挂机。

> 一个 skill，装完就退场；一套规则，跟着仓库文件走，任何 AI 工具进来都认。

## 痛点

用多个 AI 工具（Claude Code / Codex / Cursor / Gemini CLI ...）维护同一个项目时：

- **规则漂移**：每个工具读自己的入口文件（CLAUDE.md、AGENTS.md、.cursorrules...），内容各自演化，互相矛盾
- **上下文膨胀**：单文件方案（AGENTS.md、CLAUDE.md、Memory Bank）写久了无限增长，每次会话全量塞进上下文
- **状态丢失**：会话结束，「项目进行到哪了」无处安放，下个会话从头猜
- **本能跑偏**：AI 想记录信息时默认往 CLAUDE.md 堆正文，入口文件逐渐腐烂

## 设计理念

```
                 ┌─────────────── 一次性动作（skill）───────────────┐
   新项目 ──────► │ bootstrap：建骨架 + 套模板 + 生成全部入口文件      │
   旧项目 ──────► │ retrofit：扫描 → 分类 → 迁移方案确认 → 归并        │
                 └──────────────────────┬───────────────────────────┘
                                        ▼ 产物落进仓库
   ┌─────────────────────── 日常自转（不需要 skill）──────────────────┐
   │  任何 AI 工具进入项目                                            │
   │    → 自动读入口文件（3 行，只做指向）                             │
   │    → 读 PROJECT.md（≤60 行：索引 + 自维护规则）                  │
   │    → 按任务按需加载 docs/ 下 1~2 个文件（单文件 ≤300 行）          │
   │    → 发现偏差（入口被污染/文档超长/索引失效）直接自修复             │
   └──────────────────────────────────────────────────────────────────┘
```

1. **单一事实源**：PROJECT.md 只做索引和总览，永久 ≤60 行；正文细节全在它指向的子文档
2. **按需加载**：索引条目带触发条件（什么任务读什么文件），AI 对号入座，不做全量加载
3. **规则随产物走**：自维护规则内联在产物里，换没有本 skill 的工具、换一台机器，体系照常运转
4. **一次性安装器**：skill 只负责 bootstrap / retrofit，跑完退场，不参与日常维护

## 产物结构

```
project/
├── CLAUDE.md              # 1 行：@PROJECT.md（Claude Code）
├── AGENTS.md              # 1 行指向（Codex / Zed / Amp / 新版 Cursor）
├── GEMINI.md              # 1 行指向（Gemini CLI）
├── .cursor/rules/         # Cursor
├── .github/copilot-instructions.md   # GitHub Copilot
├── .windsurf/rules/       # Windsurf
├── .clinerules            # Cline
├── PROJECT.md             # ★ 唯一事实源：索引 + 自维护规则（≤60 行）
└── docs/
    ├── status.md          # 当前进度 / 下一步 / 挂起问题（只留当前态）
    ├── conventions.md     # 规范 + 信息落点路由 + 入口文件标准 + 坑区
    ├── attachments/       # 非文本文档原样归档（PDF / Office / 图片），索引登记引用
    └── notes/             # 主题知识，一主题一文件
```

这套产物有两种形态，bootstrap 会问你要哪种，据此决定写不写 `.gitignore`：

- **本机私有**（不进 git，每人一份）——把自己的开发上下文当作个人约束，同事不需要看到你的文档。产物整体进 `.gitignore`，避免挂在 `git status` 里被误提交
- **团队共享**（进 git，全队一份）——把项目规则和状态统一给所有人

两种都成立，区别只在协作者看不看得到你的文档。

支持入口文件的 AI 工具：**Claude Code、Codex、Cursor、Gemini CLI、GitHub Copilot、Windsurf、Cline**，小众工具（Kilo Code、Trae、Aider）按需补建。已存在的入口文件不覆盖，只改写为指向。

## 核心规则（内联在产物中，所有会话生效）

| 规则 | 内容 |
|---|---|
| 优先级 | 仓库内文档 > 工具本地记忆 > AI 自由发挥 |
| 信息落点 | 记录前先对号入座：约定→conventions、进度→status、知识→notes；禁止向入口文件写正文 |
| 开场对账 | 按 status.md 的对账锚点查该提交之后的改动，按作者分流；他人改动只在会话里报告，是否记入文档由你当场定 |
| 落文档纪律 | 只写结果（一行结论 + 文件路径 + 当前态），不写过程；坑一行一条，只记会再踩的 |
| 索引防腐 | 修改 PROJECT.md 结构需用户确认；索引指向的文件必须存在；单文档 >300 行即拆 |
| status 原则 | 只留当前态；挂起问题逐条保留直到解决 |
| 凭据 | 任何产物文档禁止出现真实凭据，一律写占位符；真实值只在环境变量/配置中心 |
| 版本标记 | 规则集版本，同时标记在 PROJECT.md 与 docs/conventions.md 顶部；规则或流程变更必须 bump，存量项目可逐文件比对、可同步 |

## 安装

复制到 Claude Code 的用户级 skill 目录（所有项目可用）：

```bash
# macOS / Linux
git clone https://gitee.com/ls-990703/project-hub.git ~/.claude/skills/project-hub

# Windows (PowerShell)
git clone https://gitee.com/ls-990703/project-hub.git "$env:USERPROFILE\.claude\skills\project-hub"
```

## 使用

在任意项目里对 Claude Code 说：

```
/project-hub
# 或自然语言：为这个项目初始化维护架构 / 把这个项目的文档整理成维护体系
```

skill 自动判断模式：

- 项目干净（无 PROJECT.md 无文档）→ **bootstrap**：直接建架构
- 项目有散落文件（文档、SQL、脚本、配置……不限格式）→ **retrofit**：先按通用原则判断每个文件的性质（给人读的**文档** vs 给机器用的**工程工件**）、归属（AI 产物 vs 用户原创）、破坏面（有无外部引用），产出迁移方案表，**你确认后才动文件**。文档按三分类归并，工件按项目已有惯例归位，非文本文档原样归档登记引用，分主题分批执行，拿不准的一律不动
- 已有 PROJECT.md → **无事可做，直接退出**

之后日常使用不需要 skill：任何 AI 工具进入项目都会自动按索引加载、按自维护规则运转。日常只需三件事：

```bash
git add -A && git commit -m "做了什么" && git push   # 换工具前先提交
```

## 与其他方案对比

| | 单文件方案<br>(AGENTS.md / CLAUDE.md) | Memory Bank 类 | **project-hub** |
|---|---|---|---|
| 跨工具一致 | ✗ 各读各的 | ✗ 绑定特定工具 | ✓ 入口统一指向一份事实源 |
| 上下文开销 | 随内容无限膨胀 | 每次会话全量加载 | 索引 ≤60 行 + 按需加载，结构封顶 |
| 会话间状态 | 无 | 有，但混入知识文件 | status.md 只留当前态 |
| AI 跑偏免疫 | 无 | 无 | 入口污染自动迁移归位、超长自动拆分 |
| 依赖特定 skill | — | — | 无（安装后产物自转） |

## 已知限制

下面是设计取舍，不是待修的 bug。清楚它不解决什么，比以为它全能更有用：

- **工具自带记忆不在管辖范围**：Claude Code 等工具有自己的项目级记忆目录，不进 git，也不受本体系约束。跨工具或跨机器时，只存在工具记忆里的信息会丢。需要长期保留的一律自己转写进 `docs/`。
- **锚点失效时会回退**：对账锚点丢失、或指向的提交被改写（仓库做过 rebase / 强推）时，会回退为查看最近 30 条提交并说明原因——回退区间之外的改动可能漏掉。
- **文档不进 git 时，status.md 没有历史留存**：status.md 只留当前态，若这套文档不进 git，旧状态不会在任何地方保存。需要留痕的重要节点请自行写入 `docs/notes/` 或挂起问题。
- **入口文件的指向依赖工具自觉**：本体系靠「入口文件只做指向」省上下文，但没有任何机制强制某个 AI 工具真去读 PROJECT.md。工具的指令遵循度决定实际效果。
- **自修复是静默的**：日常会话发现入口文件被污染、文档超长、索引失效，会直接修复而不询问你，也不当场通知。这是刻意的（省掉每次会话的打断），但意味着 CLAUDE.md / AGENTS.md 这类入口文件可能在你不察觉时被改写——介意的话可自行收紧这条规则。

## FAQ

**为什么入口文件只有 3 行？**
入口文件是所有工具每次会话的必读项，是唯一不能「按需」的内容——所以它必须小到可以忽略。真正的规则住在产物里，通过指向加载。

**和 AGENTS.md 标准是什么关系？**
AGENTS.md 被保留为入口之一（它已是跨工具事实标准），但 project-hub 解决的是它没解决的问题：单文件膨胀和内容无路由。

**多人项目怎么办？**
开场对账按 git 记录的**作者**分流：作者是你自己的，是自己会话的改动；是别人的，说明队友动了代码。队友的改动只在会话里报告（谁、何时、改了哪些文件），要不要记进 status.md 由你当场决定。

这套机制**不依赖任何提交格式约定**——队友好不好好写 commit message 都不影响，因为作者字段是 git 强制记录的，不是靠自觉填的。

**必须用 Claude Code 吗？**
只在安装和初始化时需要。产物是纯 markdown + git，装完之后用任何工具、甚至纯手工维护都成立。

**旧项目里大量非 markdown 文档（PDF、Word、Excel、图片）怎么办？**
不强行转换。原样归档进 `docs/attachments/`，在索引里登记一行引用（文件名 — 一句话说明），保证可发现、按需打开——转 md 既丢信息又烧上下文，登记引用才是对的。

**文档特别多，迁移会不会一次吞掉所有文件？**
不会。retrofit 先出迁移方案表等你确认，执行时按主题分批——一次一个主题，每批归并完过目后再下一批。

**迁移会不会弄断别人手里的文档链接？**
破坏面评估前置：移动任何文件前先查「谁在引用这个路径」（代码、CI、wiki、发给同事的链接）。有外部引用的默认原地不动、仅索引登记；迁移需你明确确认并知会相关方。原则是可发现优先于归位——链接断裂的代价远大于目录不整齐。

**skill 没列举过的文件类型怎么办？**
retrofit 顶层是六条通用判断原则（性质先于格式、项目惯例优先、破坏面评估前置、可发现优先于归位、归属区分、保守兜底），不是枚举式清单。任何未列举的场景都由原则推导，推导不出的一律待定、问你——宁可漏迁，不可错迁。
